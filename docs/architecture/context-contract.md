# The Project Context Contract (`.qa/context.md`)

The canonical specification of `.qa/context.md` — the file [qa-init](../../skills/qa-init/README.md) generates and every other skill reads first. It is the pack's central shared state: understand the repository once, record it, and let every skill build on that understanding instead of re-deriving it. The decision to centralize context this way is recorded in [ADR-0004](ADR-0004-project-context.md).

## Design

`.qa/context.md` has two halves, by design:

- **YAML frontmatter** — the machine-readable profile. Structured, typed, and stable, so deterministic tooling (from Milestone 4) can parse it without natural-language interpretation (principle 1: [deterministic over probabilistic](../engineering-principles.md)).
- **Markdown body** — the human-readable narrative. Editable by the team, it records assumptions, gaps, and local knowledge that detection cannot infer.

The frontmatter is the source of truth for facts; the body is the source of truth for judgment. A skill reads the frontmatter to decide *what* the project is and the body to understand *how* the team works.

The file lives at `.qa/context.md` in the consumer's repository. Teams commit it: it is shared context, and committing it means every developer and CI run sees the same profile. It is regenerated by re-running `qa-init`, and it is safe to hand-edit — `qa-init` preserves the human-authored body sections on regeneration (an obligation on the Milestone 4 implementation, noted in ADR-0004).

## Frontmatter fields

Standard YAML — unlike a `SKILL.md`, this file is a generated artifact and may use the full YAML grammar. All fields are present in every generated file; a value that could not be determined is `null` (never omitted, so the shape is stable), and low-certainty values are flagged in the `assumptions` body section.

| Field | Type | Meaning |
| --- | --- | --- |
| `schemaVersion` | integer | Version of this contract the file conforms to. Currently `1` |
| `generatedBy` | string | The skill and version that wrote the file, e.g. `qa-init@0.1.0` |
| `generatedAt` | string | ISO 8601 UTC timestamp of generation |
| `repository.root` | string | Repository root relative to the file |
| `repository.monorepo` | boolean | Whether multiple packages/projects were detected |
| `repository.packages` | array | For monorepos, each detected package: `{ path, language, testFramework }` |
| `language.primary` | string | Dominant implementation language |
| `language.others` | array | Additional languages in significant use |
| `runtime` | map | Detected runtimes and versions, e.g. `{ node: "20.x" }` |
| `packageManager` | string | `npm`, `pnpm`, `yarn`, `maven`, `gradle`, `pip`, `poetry`, `nuget`, or `null` |
| `buildTool` | string | Build system if distinct from the package manager, else `null` |
| `testFramework.unit` | string | Unit-test framework, or `null` |
| `testFramework.e2e` | string | End-to-end framework: `playwright`, `selenium`, `cypress`, `webdriverio`, or `null` |
| `testFramework.bdd` | string | BDD layer: `cucumber` or `null` |
| `browserAutomation.tool` | string | Primary browser-automation tool, or `null` |
| `browserAutomation.mcp` | boolean | Whether a relevant MCP server (Playwright, Chrome DevTools) is configured |
| `apiStyles` | array | API styles under test: any of `rest`, `graphql`, `websocket` |
| `ci.provider` | string | `github-actions`, `jenkins`, `gitlab-ci`, `azure-devops`, or `null` |
| `ci.workflows` | array | Paths to detected CI configuration files |
| `conventions.testDir` | string | Primary directory holding tests |
| `conventions.specGlob` | string | Glob matching test files |
| `conventions.configFiles` | array | Paths to detected test/tool configuration files |
| `existingAutomation` | boolean | Whether meaningful test automation already exists |
| `confidence` | string | Overall detection confidence: `high`, `medium`, or `low` |

## Body sections

Fixed headings, in this order. `qa-init` writes the detected content; the last two are owned by the team and preserved across regeneration.

| Section | Owner | Contents |
| --- | --- | --- |
| `## Summary` | qa-init | One paragraph: what this project is, in QA terms |
| `## Detected stack` | qa-init | Human-readable rendering of the frontmatter, with the evidence for each detection |
| `## Conventions` | qa-init | Where tests live, how they are named and grouped, how they run |
| `## Assumptions and gaps` | qa-init | Every low-confidence detection and every fact that could not be determined, stated plainly |
| `## Human notes` | team | Local knowledge detection cannot infer: environments, known-flaky areas, ownership. **Never contains secrets — environment-variable names only** ([SECURITY.md](../../SECURITY.md)) |

## How skills use it

Every skill's first procedural step is to read `.qa/context.md`. If it is absent, the skill stops and recommends running `qa-init` rather than guessing at the stack — reading a wrong guess is worse than reading nothing. Skills read only the fields they need and tolerate `null`: a skill that needs the e2e framework and finds `null` asks or degrades, it does not assume.

Skills treat the frontmatter as authoritative for facts and the `## Human notes` section as authoritative for team judgment. When a human note contradicts a detected fact, the skill surfaces the conflict rather than silently preferring one.

## Compatibility

`schemaVersion` governs this contract. A new optional field or body section is additive and does not raise the version. Removing or renaming a field, or changing a field's type or meaning, raises `schemaVersion` and is a major change under [ADR-0003](ADR-0003-versioning-strategy.md), shipped with a migration note.

The frontmatter is now machine-validatable against `shared/analysis/schemas/context.schema.json`, checked by the analysis platform's contract validator (Milestone 6). This document remains the authority on *meaning*; the schema enforces *shape*, and the two are kept consistent by review.
