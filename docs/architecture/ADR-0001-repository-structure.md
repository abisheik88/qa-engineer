# ADR-0001: Repository structure — single repository, single release unit

- **Status:** Accepted
- **Date:** 2026-07-17

## Context

The project comprises several kinds of artifact that must stay mutually consistent: canonical skills, single-sourced knowledge modules, deterministic analyzer scripts, an installer CLI, scaffolding templates, an evaluation harness, and documentation. A skill references knowledge modules; the installer materializes both; the evaluation harness asserts against the behavior of all three. A version of one is only meaningful relative to specific versions of the others.

The structure must also serve two audiences at once: QA engineers contributing prose and skills with minimal tooling friction, and maintainers who need CI to hold every layer to the same bar. Finally, ecosystem conventions reward a repository whose `skills/` directory sits at the root in standard form, because skill-installation tooling across agents consumes repositories in that shape directly.

## Decision

One repository, one release unit, with this top-level layout:

| Path | Role |
| --- | --- |
| `skills/` | Canonical Agent Skills — the shippable product, in standard form at the repository root |
| `shared/` | Single-source knowledge modules (domains, frameworks, stacks, CI), synced into skills by copy |
| `packages/` | Installer CLI and documentation tooling (Node.js workspaces, added in Milestone 4) |
| `scripts/` | Repository maintenance tooling: sync, validation, release helpers |
| `templates/` | Scaffolds for new skills and knowledge modules |
| `tests/` | Validation and evaluation harness: fixtures, golden tasks, baselines |
| `examples/` | Public demo application and integration walkthroughs |
| `docs/` | Architecture records, installation guides, contributor standards |
| `.github/` | Community health files, issue forms, CI workflows |

Placement rules that follow from the layered architecture:

- QA analyzer scripts live inside the skill that owns them (`skills/<name>/scripts/`), not in the top-level `scripts/` directory, so every installed skill is self-contained.
- `shared/` is the only place cross-skill knowledge is edited; the copies inside `skills/*/references/` are generated by the sync tool and guarded against manual edits by CI.
- The evaluation harness and its fixtures live in `tests/` and are excluded from any published artifact.

Everything in the repository versions and releases together, as specified in [ADR-0003](ADR-0003-versioning-strategy.md).

## Alternatives considered

- **Multi-package organization** (separate packages for skills, knowledge, adapters, CLI, published independently): rejected. Skills are not imported as code, so consumers gain nothing from independent versions, while the project inherits version-skew classes of bugs, four release pipelines, and cross-repository pull requests for single logical changes.
- **Separate community-skills repository from day one** (stable core plus community-contributed satellite): deferred, not rejected. The split is proven in the ecosystem but only pays once sustained external contribution exists; adopting it now doubles maintenance surface with zero contributors. Revisit at Milestone 6.
- **`src/` plus generated `dist/` split** (canonical sources compiled into per-agent output trees): rejected as a structural consequence of [ADR-0002](ADR-0002-agent-skill-standard.md) — there is no compile step, so there is nothing to put in a `dist/`.

## Consequences

- Lockstep versioning is guaranteed structurally: a single commit describes the exact state of skills, knowledge, tooling, and evaluations.
- Contributors have one clone, one set of conventions, and one place to open pull requests; CI applies the same quality gates to every layer.
- The repository will grow large as evaluation fixtures accumulate; published artifacts must therefore be built from explicit allowlists rather than repository snapshots, and heavy fixtures must stay out of installable paths.
- Reserved directories exist before their milestones fill them; each must carry a README stating its purpose and owning milestone so the repository never presents unexplained empty space.
- A future community-repository split remains possible without breaking this decision, because `skills/` in standard form is portable by construction.
